# Контракт интеграции frontend с backend

## Модуль скоринга по правилам

С 23 октября 2026 доступна Python-функция `backend.src.scoring.score_company(company, evaluated_at=...)`.
Её входы и правила описаны в `docs/ds_contract.md`, порядок внедрения — в `docs/ds_plan.md`.
Модуль пока не подключён к endpoint'ам и demo-store. Перед HTTP-интеграцией backend должен описать DTO в OpenAPI.
Существующие поля `score`, `riskLevel`, `summary`, `factors` сохраняются. Добавлены метаданные
`modelVersion`, `featureVersion`, `calculatedAt`, `eventProbability` (null у правил),
а в факторы — `code`, `points`, `maxPoints`. В TypeScript они пока необязательны для совместимости с demo-store.
`hasOverdue` означает действующую просроченную задолженность на дату оценки. Старое поле компании
`scoringScore` не является входом нового расчёта. Только score недостаточно для одобрения:
проверки статуса компании, просрочки, документов и доступности нового платежа выполняются отдельно.

Frontend работает автономно на синтетических данных. Для перехода с demo-store на API нужно согласовать и реализовать контракт ниже.

## Обязательные endpoint'ы

Стресс-сценарии: `backend.src.scoring.stress_financing`, контракт `docs/stress_contract.md`.
Показывать фиксированные предположения рядом с результатом. Запас снижения выручки
относится только к покрытию, не к одобрению. null означает отсутствие допустимого
запаса/нулевую выручку; его нельзя отображать как 0%. В сценариях сохраняется
исходная сумма кредита, даже если evaluation содержит уменьшенную альтернативу.

Подбор нескольких вариантов: `backend.src.scoring.recommend_financing`, контракт
`docs/ranking_contract.md`. Возвращает пять отдельных групп и rankInGroup;
preference=min_interest (по умолчанию) или min_payment. Другие сроки и меньшие суммы
показываются явно как альтернативы. API пока не подключён; OpenAPI требует отдельной
адаптации. evaluation относится к исходной сумме, offer — к показываемому варианту.

Для серверных расчётов доступен также `backend.src.scoring.assess_financing`:
платёж, покрытие, причины ограничений и проверенная альтернативная сумма.
Контракт — `docs/financing_contract.md`. Это внутренний DTO, пока не подключённый к API:
он не заменяет напрямую frontend Recommendation. При адаптации `eligible` относится
к исходному запросу, а `alternative` содержит отдельно проверенные условия.
`assessment` нельзя записывать как статус заявки. Формат денег — рубли с копейками;
регулярный платёж округляется вверх до копейки, в отличие от старого frontend-демо
с округлением до рубля. После интеграции frontend должен отображать серверный результат.

## Канонические статусы

Frontend использует следующие коды:

```text
review → need_info → review
review → offer → sign → ready → disbursed
review → rejected
offer → rejected
```

Полный список:

- `review`
- `need_info`
- `offer`
- `sign`
- `ready`
- `disbursed`
- `rejected`

Backend должен быть единственным владельцем допустимых переходов и проверять роль инициатора.

## Уведомления в реальном времени

В репозитории уже есть frontend-клиент с переподключением и локальный relay в `realtime-server`. URL задаётся переменной `VITE_WS_URL`, по умолчанию в development используется `ws://localhost:8080`.

Формат сообщения:

```json
{
  "id": "уникальный-id-события",
  "sentAt": "2026-10-22T13:25:00.000Z",
  "type": "application.updated",
  "payload": {
    "application": {}
  }
}
```

Поддерживаемые типы:

- `application.updated` — payload содержит полную актуальную заявку;
- `notification.created` — payload содержит полное уведомление;
- `notification.read` — payload содержит `notificationId`.

Локальный relay не хранит данные и не проверяет пользователя. В production backend или API gateway должен аутентифицировать соединение, фильтровать события по роли и компании и оставаться источником истины. Polling использовать только как резервный режим.

## Запрос рекомендаций

```json
{
  "purpose": "goods",
  "amount": 800000,
  "termMonths": 24
}
```

Ожидаемый элемент ответа:

```json
{
  "product": {
    "id": "working-capital",
    "name": "Оборотный кредит",
    "rate": 24,
    "minAmount": 100000,
    "maxAmount": 3000000,
    "terms": [12, 24, 36]
  },
  "monthlyPayment": 42297,
  "coverage": 0.99,
  "eligible": false,
  "reason": "Подходит по параметрам каталога, но требует решения сотрудника банка",
  "warning": "Расчётная нагрузка выше автоматического порога",
  "recommendedAmount": 150000
}
```

Frontend не должен пересчитывать ставку, платёж, покрытие, скоринг или рекомендуемую сумму после подключения API.

## Решение банка

```json
{
  "kind": "alternative",
  "amount": 150000,
  "termMonths": 24,
  "rate": 24,
  "comment": "Сумма снижена для достижения покрытия 1,25×"
}
```

`kind`:

- `approve`
- `alternative`
- `need_info`
- `reject`

Для `alternative` обязательны сумма, срок, ставка и комментарий. Для `need_info` и `reject` обязателен комментарий.

## Требования к заявке

Ответ карточки заявки должен содержать:

- идентификатор, компанию, продукт, цель, сумму и срок;
- текущий статус и время изменения;
- ставку, платёж и коэффициент покрытия;
- скоринговый балл, риск, объяснение и факторы;
- проверки ФНС, БКИ и документов;
- активный оффер;
- комментарий банка;
- упорядоченную историю событий с инициатором.

## Ошибки

Нужен единый формат:

```json
{
  "code": "INVALID_STATUS_TRANSITION",
  "message": "Заявку нельзя подписать в текущем статусе",
  "fieldErrors": {
    "amount": "Сумма выходит за диапазон продукта"
  }
}
```

Ожидаемые HTTP-коды:

- `401` — сессия отсутствует или истекла;
- `403` — действие запрещено роли;
- `404` — сущность не найдена;
- `409` — статус заявки уже изменился;
- `422` — ошибка данных формы;
- `500` — внутренняя ошибка.

## Задача backend-разработчика

Backend должен заменить demo-store из frontend и стать единственным источником данных. Frontend после интеграции только показывает полученные значения и отправляет команды пользователя: он не должен самостоятельно менять статус заявки, рассчитывать оффер или решать, разрешено ли действие.

Все HTTP-маршруты рекомендуется публиковать с префиксом `/api/v1`. Например, полный адрес списка заявок при локальном запуске: `http://localhost:8000/api/v1/applications`.

### 1. Подготовить модели и хранение

Минимально нужны следующие сущности:

- `User`: `id`, `email`, хеш пароля, имя, роль `client | bank`, `companyId` для клиента;
- `Company`: реквизиты, отрасль, оборот, расходы, текущая долговая нагрузка и документы;
- `CreditProduct`: код, название, ставка, допустимые суммы, сроки и цели;
- `Application`: компания, продукт, запрошенные условия, расчёты, статус и даты;
- `BankDecision`: тип решения, сумма, срок, ставка, комментарий и автор;
- `ApplicationEvent`: заявка, тип события, старый и новый статус, автор и время;
- `Notification`: получатель, тип, заголовок, текст, признак прочтения и время.

Идентификаторы должны быть стабильными строками. Frontend уже использует значения наподобие `APP-2026-003`, поэтому backend либо хранит такой публичный ID, либо возвращает его отдельно от внутреннего числового ID.

Изменение заявки, запись события и создание уведомления нужно выполнять в одной транзакции. Нельзя сначала вернуть успешный ответ, а затем отдельно пытаться сохранить историю.

### 2. Реализовать авторизацию и роли

`POST /api/v1/auth/login` принимает:

```json
{
  "email": "client@demo.ru",
  "password": "123456"
}
```

При успешном входе backend создаёт сессию или выдаёт токен и возвращает пользователя:

```json
{
  "user": {
    "id": "user-client-city",
    "name": "Алексей Смирнов",
    "email": "client@demo.ru",
    "role": "client",
    "companyId": "company-city"
  }
}
```

Предпочтительный вариант — защищённая `HttpOnly` cookie. Если используется Bearer token, его формат, время жизни и способ обновления нужно описать в OpenAPI.

`GET /api/v1/me` должен возвращать пользователя текущей сессии. `companyId` нельзя принимать от клиента как доказательство доступа: компания определяется по авторизованному пользователю.

Права:

- `client` видит профиль и заявки только своей компании;
- `client` создаёт заявку, отправляет сведения, принимает оффер и подписывает его;
- `bank` видит банковскую очередь и принимает решение;
- выдачу выполняет роль, которую подтвердит команда;
- пользователь другой компании получает `404`, чтобы не раскрывать существование чужой заявки;
- пользователь с неподходящей ролью получает `403`.

### 3. Реализовать профиль и каталог

`GET /api/v1/companies/me` возвращает данные компании текущего клиента, например:

```json
{
  "id": "company-city",
  "name": "Магазин «Город»",
  "inn": "7701234567",
  "industry": "retail",
  "monthlyRevenue": 1200000,
  "monthlyExpenses": 850000,
  "currentMonthlyDebtPayment": 50000,
  "documents": [
    {
      "id": "doc-1",
      "name": "Выписка по счёту",
      "status": "verified"
    }
  ]
}
```

`GET /api/v1/credit-products` возвращает массив продуктов. Фильтрацию можно добавить query-параметрами, но frontend должен иметь возможность получить полный каталог одним запросом.

### 4. Реализовать расчёт рекомендаций

`POST /api/v1/recommendations` получает цель, сумму и срок из примера выше. Backend должен:

1. Найти продукты, допускающие указанную цель, сумму и срок.
2. Рассчитать аннуитетный ежемесячный платёж.
3. Учесть существующую долговую нагрузку компании.
4. Рассчитать коэффициент покрытия по согласованной формуле.
5. Определить `eligible`, предупреждение и причину.
6. Если нагрузка слишком высокая, рассчитать `recommendedAmount`.
7. Вернуть результаты в порядке от наиболее подходящего к наименее подходящему.

Все денежные вычисления выполняются на backend с согласованным округлением. Frontend не должен повторять эти формулы. Пока аналитик не утвердил формулы, их нужно вынести в отдельный сервис и покрыть тестами, чтобы позднее заменить без изменения API.

### 5. Реализовать жизненный цикл заявки

`POST /api/v1/applications` принимает выбранный продукт и условия:

```json
{
  "productId": "working-capital",
  "purpose": "goods",
  "amount": 800000,
  "termMonths": 24
}
```

Backend должен повторно проверить продукт и условия, выполнить актуальный расчёт, создать заявку со статусом `review`, записать первое событие и вернуть полную созданную заявку. Нельзя доверять рассчитанным frontend значениям платежа, ставки или покрытия.

`GET /api/v1/applications` для клиента возвращает только заявки его компании. Для фильтрации можно поддержать `status`, а для пагинации — `limit` и `offset` либо `page` и `pageSize`.

`GET /api/v1/applications/{id}` возвращает полную карточку. Желательно использовать один и тот же DTO во всех ответах и в событии `application.updated`, чтобы frontend не собирал заявку из разных несовместимых форматов.

`POST /api/v1/applications/{id}/additional-info` принимает ответ клиента:

```json
{
  "comment": "Прикладываем уточнённую выписку",
  "documentIds": ["doc-2"]
}
```

Команда допустима только в `need_info`, после неё заявка возвращается в `review`.

`POST /api/v1/applications/{id}/accept` принимает:

```json
{
  "accepted": true
}
```

При `true`: `offer → sign`. При `false`: `offer → rejected`. Повторный запрос не должен незаметно менять уже обработанную заявку; вернуть актуальный объект при идемпотентном повторе либо `409` при конфликте.

`POST /api/v1/applications/{id}/sign` выполняет `sign → ready`. Для MVP допустимо демоподписание, но backend всё равно фиксирует дату, пользователя и событие.

`POST /api/v1/applications/{id}/disburse` выполняет `ready → disbursed`. Backend должен проверить роль инициатора и не принимать сумму выдачи с frontend.

### 6. Реализовать банковскую очередь и решения

`GET /api/v1/bank/applications` доступен только роли `bank`. Ответ может поддерживать фильтры `status`, `search`, сортировку и пагинацию.

`POST /api/v1/bank/applications/{id}/decision` принимает тело из раздела «Решение банка» и обрабатывает его так:

| `kind` | Допустимый исходный статус | Новый статус | Обязательные поля |
|---|---|---|---|
| `approve` | `review` | `offer` | подтверждённые сумма, срок и ставка |
| `alternative` | `review` | `offer` | сумма, срок, ставка, комментарий |
| `need_info` | `review` | `need_info` | комментарий |
| `reject` | `review` или `offer` | `rejected` | комментарий |

Для `approve` backend может взять уже рассчитанные условия заявки, но в ответе всё равно должен присутствовать полноценный оффер. Для `alternative` нужно проверить положительную сумму, допустимый срок и ставку. При устаревшем статусе вернуть `409 INVALID_STATUS_TRANSITION`.

После решения backend в одной транзакции:

1. проверяет права и текущий статус;
2. сохраняет решение или оффер;
3. меняет статус заявки;
4. записывает `ApplicationEvent`;
5. создаёт уведомление клиенту;
6. фиксирует транзакцию;
7. отправляет realtime-события.

### 7. Зафиксировать таблицу переходов

Backend должен централизовать переходы в одном сервисе, а не проверять их разрозненно в каждом роуте:

| Из статуса | В статус | Кто выполняет | Команда |
|---|---|---|---|
| `review` | `need_info` | `bank` | решение `need_info` |
| `need_info` | `review` | `client` | отправка сведений |
| `review` | `offer` | `bank` | `approve` или `alternative` |
| `review` | `rejected` | `bank` | решение `reject` |
| `offer` | `sign` | `client` | принятие оффера |
| `offer` | `rejected` | `client` или `bank` | отказ |
| `sign` | `ready` | `client` | подписание |
| `ready` | `disbursed` | согласованная роль | выдача |

Любой другой переход должен завершаться `409`, а состояние заявки не должно изменяться.

### 8. Реализовать уведомления и WebSocket

`GET /api/v1/notifications` возвращает уведомления только текущего пользователя. Желательно поддержать `unreadOnly=true` и пагинацию.

`POST /api/v1/notifications/{id}/read` помечает уведомление прочитанным, возвращает обновлённое уведомление и публикует `notification.read`.

Production WebSocket должен работать по `/api/v1/realtime` или по отдельно согласованному URL. При подключении backend обязан установить пользователя из cookie или короткоживущего WS-токена. Передавать постоянный access token в query string нежелательно: он может попасть в логи.

Маршрутизация событий:

- клиент получает изменения только заявок своей компании и свои уведомления;
- сотрудник банка получает изменения банковской очереди;
- после каждого изменения заявки отправляется `application.updated` с полной актуальной заявкой;
- после создания уведомления отправляется `notification.created`;
- после прочтения — `notification.read`;
- `id` события уникален, `sentAt` записан в UTC в формате ISO 8601.

Сначала данные нужно сохранить в БД и только потом отправлять событие. Для надёжной production-доставки рекомендуется transactional outbox; для MVP допустима публикация сразу после успешного commit.

### 9. Настроить ошибки, CORS и документацию

Добавить общий обработчик исключений, который всегда возвращает формат из раздела «Ошибки». В `500` нельзя отдавать stack trace, SQL или секреты. Детали ошибки записываются в серверный лог вместе с request ID.

Для локальной разработки разрешить точный origin Vite, обычно `http://localhost:5173`. Если авторизация на cookie, включить credentials и нельзя использовать `Access-Control-Allow-Origin: *`.

OpenAPI должен описывать:

- request и response schema без голых `dict`;
- примеры успешных ответов;
- ответы `401`, `403`, `404`, `409` и `422`;
- способ авторизации;
- enum ролей, статусов и видов решения.

Swagger FastAPI обычно доступен по `/docs`, JSON-схема — по `/openapi.json`.

### 10. Что поправить в текущем backend-каркасе

В принятом каркасе уже есть FastAPI-маршруты под `/api/v1`, но перед интеграцией нужно исправить следующее:

- опечатку `/bank/applicationss` заменить на `/bank/applications`;
- унифицировать `/applications/{id}/provide-info` с контрактом `/applications/{id}/additional-info`;
- не принимать `company_id` из query для пользовательских заявок, а брать компанию из авторизации;
- добавить Pydantic-схемы вместо возврата `dict` и `list[dict]`;
- передать тело решения в `POST /bank/applications/{id}/decision`;
- добавить `Session` и транзакцию в `sign` и `disburse`;
- реализовать отсутствующие auth, notifications и realtime-маршруты;
- добавить CORS, обработчики ошибок и конфигурацию секретов;
- убрать создание таблиц через `Base.metadata.create_all` при запуске production и подключить миграции Alembic.

### 11. Рекомендуемый порядок работы

1. Описать Pydantic DTO и SQLAlchemy-модели, подключить миграции.
2. Добавить seed-команду для тестовых пользователей, компаний и продуктов.
3. Реализовать login, `/me`, роли и зависимость текущего пользователя.
4. Реализовать профиль компании и каталог.
5. Вынести расчёты в сервис и покрыть unit-тестами.
6. Реализовать создание и чтение заявок.
7. Реализовать state machine и банковские решения.
8. Реализовать действия клиента: сведения, оффер, подписание и выдачу.
9. Добавить уведомления и WebSocket поверх уже работающих транзакций.
10. Описать API в Swagger и провести интеграцию с frontend.

### 12. Критерии готовности backend MVP

Backend можно передавать frontend-разработчику, когда:

- новый пользователь может войти, а `/me` возвращает его роль;
- клиент не может прочитать заявку другой компании;
- сотрудник банка не может вызвать клиентское действие и наоборот;
- каталог и рекомендации возвращают DTO из этого документа;
- заявка проходит полный сценарий `review → offer → sign → ready → disbursed`;
- сценарий `review → need_info → review` работает с историей событий;
- невалидный переход возвращает `409` без изменения БД;
- банковское решение создаёт уведомление клиенту;
- две открытые вкладки получают обновление через WebSocket;
- после перезагрузки страницы состояние восстанавливается из backend, а не из `localStorage`;
- Swagger содержит схемы и примеры;
- unit-тесты проверяют расчёты и переходы статусов;
- API-тесты проверяют авторизацию, разграничение компаний и основные happy/error paths.

## Технические условия

- OpenAPI/Swagger должен быть доступен команде frontend.
- Способ авторизации: предпочтительно HttpOnly cookie; альтернатива — Bearer token.
- Для локальной разработки нужен CORS с адреса Vite.
- Базовый адрес API будет передаваться через `VITE_API_URL`.
- Деньги передаются числом в рублях, даты — ISO 8601, коэффициенты — числом без форматирования.
