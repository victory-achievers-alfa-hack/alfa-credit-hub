# Контракт интеграции frontend с backend

Frontend работает автономно на синтетических данных. Для перехода с demo-store на API нужно согласовать и реализовать контракт ниже.

## Обязательные endpoint'ы

| Метод | URL | Назначение |
|---|---|---|
| `POST` | `/auth/login` | Вход, серверная проверка пароля и роли |
| `GET` | `/me` | Текущий пользователь и роль |
| `GET` | `/companies/me` | Профиль компании, финансы и документы |
| `GET` | `/credit-products` | Каталог кредитных продуктов |
| `POST` | `/recommendations` | Подбор продуктов и финансовый расчёт |
| `POST` | `/applications` | Создание заявки |
| `GET` | `/applications` | Заявки текущей компании |
| `GET` | `/applications/{id}` | Заявка, проверки, оффер и события |
| `GET` | `/bank/applications` | Очередь заявок банка |
| `POST` | `/bank/applications/{id}/decision` | Решение банка |
| `POST` | `/applications/{id}/additional-info` | Ответ клиента на запрос сведений |
| `POST` | `/applications/{id}/accept` | Принятие или отклонение оффера |
| `POST` | `/applications/{id}/sign` | Демоподписание |
| `POST` | `/applications/{id}/disburse` | Моделируемая выдача |
| `GET` | `/notifications` | Уведомления текущего клиента |
| `POST` | `/notifications/{id}/read` | Отметить уведомление прочитанным |
| `WS` | `/realtime` | WebSocket-поток изменений заявок и уведомлений |

## Канонические статусы

Frontend использует следующие коды:

```text
review → need_info → review
review → offer → sign → ready → disbursed
review → rejected
offer → rejected
```

Полный список:

- `review`
- `need_info`
- `offer`
- `sign`
- `ready`
- `disbursed`
- `rejected`

Backend должен быть единственным владельцем допустимых переходов и проверять роль инициатора.

## Уведомления в реальном времени

В репозитории уже есть frontend-клиент с переподключением и локальный relay в `realtime-server`. URL задаётся переменной `VITE_WS_URL`, по умолчанию в development используется `ws://localhost:8080`.

Формат сообщения:

```json
{
  "id": "уникальный-id-события",
  "sentAt": "2026-10-22T13:25:00.000Z",
  "type": "application.updated",
  "payload": {
    "application": {}
  }
}
```

Поддерживаемые типы:

- `application.updated` — payload содержит полную актуальную заявку;
- `notification.created` — payload содержит полное уведомление;
- `notification.read` — payload содержит `notificationId`.

Локальный relay не хранит данные и не проверяет пользователя. В production backend или API gateway должен аутентифицировать соединение, фильтровать события по роли и компании и оставаться источником истины. Polling использовать только как резервный режим.

## Запрос рекомендаций

```json
{
  "purpose": "goods",
  "amount": 800000,
  "termMonths": 24
}
```

Ожидаемый элемент ответа:

```json
{
  "product": {
    "id": "working-capital",
    "name": "Оборотный кредит",
    "rate": 24,
    "minAmount": 100000,
    "maxAmount": 3000000,
    "terms": [12, 24, 36]
  },
  "monthlyPayment": 42297,
  "coverage": 0.99,
  "eligible": false,
  "reason": "Подходит по параметрам каталога, но требует решения сотрудника банка",
  "warning": "Расчётная нагрузка выше автоматического порога",
  "recommendedAmount": 150000
}
```

Frontend не должен пересчитывать ставку, платёж, покрытие, скоринг или рекомендуемую сумму после подключения API.

## Решение банка

```json
{
  "kind": "alternative",
  "amount": 150000,
  "termMonths": 24,
  "rate": 24,
  "comment": "Сумма снижена для достижения покрытия 1,25×"
}
```

`kind`:

- `approve`
- `alternative`
- `need_info`
- `reject`

Для `alternative` обязательны сумма, срок, ставка и комментарий. Для `need_info` и `reject` обязателен комментарий.

## Требования к заявке

Ответ карточки заявки должен содержать:

- идентификатор, компанию, продукт, цель, сумму и срок;
- текущий статус и время изменения;
- ставку, платёж и коэффициент покрытия;
- скоринговый балл, риск, объяснение и факторы;
- проверки ФНС, БКИ и документов;
- активный оффер;
- комментарий банка;
- упорядоченную историю событий с инициатором.

## Ошибки

Нужен единый формат:

```json
{
  "code": "INVALID_STATUS_TRANSITION",
  "message": "Заявку нельзя подписать в текущем статусе",
  "fieldErrors": {
    "amount": "Сумма выходит за диапазон продукта"
  }
}
```

Ожидаемые HTTP-коды:

- `401` — сессия отсутствует или истекла;
- `403` — действие запрещено роли;
- `404` — сущность не найдена;
- `409` — статус заявки уже изменился;
- `422` — ошибка данных формы;
- `500` — внутренняя ошибка.

## Что должен подтвердить аналитик

1. Финальные параметры трёх продуктов и демонстрационные ставки.
2. Канонические коды и подписи статусов.
3. Кто имеет право выполнять `ready → disbursed`.
4. Что именно клиент делает в состоянии `need_info`.
5. Обязательность ручного решения банка для всех или только пограничных заявок.
6. Формулы платежа, покрытия и балльной оценки.
7. Правило расчёта альтернативной суммы.
8. Тексты причин отказа и предупреждений.
9. Набор данных трёх тестовых компаний.
10. Приоритет новостей и ИИ-помощника относительно основного сценария.

## Технические условия

- OpenAPI/Swagger должен быть доступен команде frontend.
- Способ авторизации: предпочтительно HttpOnly cookie; альтернатива — Bearer token.
- Для локальной разработки нужен CORS с адреса Vite.
- Базовый адрес API будет передаваться через `VITE_API_URL`.
- Деньги передаются числом в рублях, даты — ISO 8601, коэффициенты — числом без форматирования.
