# Контракты API и принятия решений

Этот документ фиксирует фактический контракт интеграции frontend, backend и расчётных модулей проекта «Альфа / Поток». Он описывает текущее поведение runtime-кода, а не план внедрения и не банковскую кредитную политику.

## 1. Назначение и границы

### 1.1. Назначение

Система реализует демонстрационный кредитный путь для предпринимателя и сотрудника банка:

1. аутентификация и загрузка профиля компании;
2. чтение каталога кредитных продуктов;
3. расчёт и ранжирование вариантов финансирования;
4. создание заявки с сохранением снимка расчёта;
5. банковское решение;
6. запрос дополнительных сведений, принятие или отклонение оффера;
7. демоподписание и моделируемая выдача;
8. уведомления и realtime-синхронизация.

Backend является источником истины для пользователей, компаний, продуктов, заявок, решений, событий, уведомлений и расчётов. Frontend передаёт пользовательские команды и отображает серверные результаты; он не должен самостоятельно рассчитывать ставку, платёж, покрытие, score, рекомендуемую сумму или допустимость перехода статуса.

### 1.2. Источники контракта

Приоритет источников:

1. **Runtime OpenAPI** по `/openapi.json` — источник DTO, обязательности полей, enum и HTTP-схем; Swagger доступен по `/docs`.
2. **Runtime-код и тесты** — источник фактической бизнес-семантики, переходов и расчётных правил.
3. **Этот документ** — нормативное объяснение семантики и границ ответственности.

Изменение публичного DTO сначала должно отражаться в Pydantic-схеме и runtime OpenAPI, затем в этом документе и frontend-типах.

Известное исключение: route-level OpenAPI для ошибок рекомендаций пока описывает legacy-обёртку `{"detail":{"code","message"}}`, тогда как приложение с глобальными exception handlers фактически возвращает плоский envelope из раздела 2.5. До устранения рассинхронизации фактический runtime-ответ имеет приоритет, а frontend временно понимает обе формы.

### 1.3. Границы решения

- Score 0–100 — детерминированная проектная эвристика устойчивости, а не вероятность дефолта, банковский рейтинг или автоматическое решение о выдаче.
- `assessment` расчётного модуля — не статус заявки.
- `eligible` означает прохождение предварительных правил для конкретных условий, а не окончательное одобрение банка.
- Банковское решение не должно основываться только на score: отдельно проверяются активность компании, текущая просрочка, документы, продукт и покрытие платежей.
- Реестры, БКИ, документы, подписание и выдача моделируются локально; интеграции с банковскими и государственными системами не заявляются.
- Все ставки, пороги, веса, продукты и данные компаний демонстрационные и не являются политикой Альфа-Банка.
- Обучаемой ML-модели в текущем контуре нет: отсутствуют валидные исторические outcomes и target contract.

### 1.4. Общие технические соглашения

- Базовый HTTP-префикс: `/api/v1`.
- WebSocket: `/api/v1/realtime`.
- Frontend использует `VITE_API_URL`, по умолчанию `/api/v1`; `VITE_WS_URL` может явно переопределить WebSocket URL.
- DTO на базе `ApiSchema` сериализуются в camelCase; отдельные mock/system DTO следует брать непосредственно из OpenAPI.
- Денежные значения во внешнем JSON передаются числами в рублях; внутренние решения вычисляются через `Decimal`.
- Даты и время передаются в ISO 8601; расчётное время нормализуется в UTC.
- Коэффициенты передаются числами без символов форматирования.
- Неизвестные поля запрещены в запросе рекомендаций. Для остальных endpoint’ов точное поведение `extra` определяется runtime OpenAPI.

## 2. Фактический API, авторизация, роли, ошибки, realtime и state machine

### 2.1. Авторизация и сессия

`POST /api/v1/auth/login` принимает:

```json
{
  "email": "client@demo.ru",
  "password": "123456"
}
```

При успехе backend:

- возвращает `accessToken`, `tokenType: "bearer"` и объект `user`;
- устанавливает cookie `access_token` с `HttpOnly`, `SameSite=Lax`, `Path=/`;
- задаёт cookie и токену срок жизни 12 часов;
- использует флаг `Secure` из `AUTH_COOKIE_SECURE`.

Защищённые HTTP endpoint’ы принимают либо `Authorization: Bearer <token>`, либо cookie `access_token`. Если одновременно передан Bearer, он имеет приоритет. Токен подписан HMAC-SHA256 и содержит `sub`, `role`, `company_id`, `iat`, `exp`; при каждом запросе роль и компания сверяются с текущей записью пользователя в БД.

`GET /api/v1/me` восстанавливает текущего пользователя. `POST /api/v1/auth/logout` удаляет browser cookie и возвращает `204`; серверного списка отозванных токенов нет, поэтому ранее выданный Bearer действует до истечения срока.

Компания клиента всегда определяется из аутентифицированного пользователя. `companyId`, query-параметр или заголовок клиента не являются доказательством доступа. Чужая или отсутствующая компания/заявка обычно возвращается как `404`, чтобы не раскрывать существование ресурса.

Cookie общая для вкладок одного browser profile. Для одновременной работы под ролями `client` и `bank` нужны разные профили браузера или инкогнито. Frontend синхронизирует login/logout между вкладками через `BroadcastChannel`.

### 2.2. Роли

| Роль | Фактические права |
|---|---|
| `client` | Читать свой профиль и заявки компании, получать рекомендации, создавать заявку, отправлять дополнительные сведения, принимать/отклонять оффер, подписывать и выполнять моделируемую выдачу, читать свои уведомления. |
| `bank` | Читать всю банковскую очередь и детали заявок, принимать решения `approve`, `alternative`, `need_info`, `reject`, получать `application.updated` через WebSocket. |

Неподходящая роль получает `403 FORBIDDEN`. Некоторые демонстрационные и системные endpoint’ы сейчас публичны; они перечислены отдельно и должны быть закрыты перед production.

### 2.4. Заявки и решения

#### Создание заявки

`POST /applications` принимает `productId`, `purpose`, `amount`, `termMonths`.

На уровне API:

- `productId` — непустая строка;
- `purpose` — `goods | equipment | cash_gap`;
- `amount` — от 50 000 до 5 000 000 рублей;
- `termMonths` — положительное целое; расчётный слой дополнительно ограничивает срок диапазоном 1–120.

Backend читает компанию и продукт из БД, повторно выполняет `assess_financing`, создаёт публичный id вида `APP-<year>-NNN`, заявку в `review`, `ApplicationCheck` со снимком входов/score/checks и событие `submitted` в одной транзакции.

Текущее поведение допускает создание заявки даже с `assessment=blocked`, `need_info`, `manual_review` или `unavailable`: assessment сохраняется в снимке, но заявка всё равно переходит в `review`. Это известный gap, а не рекомендуемая политика.

`evaluationId` предыдущего подбора не принимается и не связывается с заявкой. Создание заявки всегда является новым расчётом на текущих данных.

#### Карточка заявки

Фактический detail DTO содержит:

- идентификаторы компании и продукта, название продукта, цель;
- запрошенные сумму, срок, ставку и платёж;
- покрытие и статус;
- сохранённый scoring snapshot и checks на момент подачи;
- последний оффер `approve`/`alternative`, если есть;
- комментарий банка и `infoRequest` в статусе `need_info`;
- даты и историю событий.

Текущий score в `/companies/me` может отличаться от сохранённого score заявки. Исторический снимок заявки не пересчитывается задним числом.

#### Решение банка

`kind` принимает `approve | alternative | need_info | reject`.

- `approve`: поля условий необязательны; если переданы, должны точно совпадать с исходной заявкой, иначе `409 USE_ALTERNATIVE`.
- `alternative`: обязательны положительная `amount`, положительный `termMonths`, неотрицательная `rate` и непустой `comment`.
- `need_info` и `reject`: обязателен непустой `comment`.
- `comment` ограничен 2000 символами.

Для `approve` и `alternative` backend блокирует строку заявки для обновления, читает текущий профиль/документы/продукт, подставляет предложенную ставку и повторно вызывает `assess_financing`. Оффер создаётся только если текущий результат имеет `policyPasses=true`; иначе возвращается `409 OFFER_NOT_ELIGIBLE`, а состояние не меняется. Для score 50–69 действуют более строгие ограничения из раздела 4.6 и обязательное обоснование длиной от 20 символов после trim. При его отсутствии возвращается `409 REVIEW_JUSTIFICATION_REQUIRED`. Это путь рассмотрения в рамках политики, а не произвольный override.

Решение, переход, event, клиентское notification и снимок повторного расчёта в RecommendationAudit сохраняются одной транзакцией. Снимок решения содержит автора, обоснование, данные компании, условия продукта, результат и стресс-анализ; schemaVersion=bank-decision-audit-v1. После commit публикуются `application.updated` и `notification.created`.

Повторная оценка сохраняется в аудите решения, но не перезаписывает первоначальный ApplicationCheck. Карточка показывает первоначальный snapshot заявки, явно отделённый от предложения банка. Для `alternative` backend также не проверяет отдельным правилом, что предложение строго меньше исходной суммы: оно должно лишь пройти общий продуктовый и финансовый расчёт.

### 2.5. Ошибки

Фактический глобальный runtime-envelope:

```json
{
  "code": "INVALID_STATUS_TRANSITION",
  "message": "Описание ошибки",
  "fieldErrors": null
}
```

Для `422` `fieldErrors` — словарь `поле → сообщение`, построенный из Pydantic validation locations:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "fieldErrors": {
    "amount": "Input should be greater than 0"
  }
}
```

Основные HTTP-коды:

| Код | Семантика |
|---|---|
| `401` | Нет/истёк/некорректен token или неверные credentials. |
| `403` | Роль не имеет права на действие. |
| `404` | Ресурс отсутствует или скрыт из-за отсутствия владения. |
| `409` | Конфликт состояния или серверных исходных данных: невалидный переход, невозможный оффер, требование использовать alternative и т. п. Это не обязательно кредитный отказ. |
| `422` | Запрос не соответствует DTO. |
| `503` | Недоступна БД/источник, невалиден результат расчёта или не удалось сохранить обязательный аудит. |
| `500` | Необработанная внутренняя ошибка; stack trace клиенту не возвращается. |

Значимые machine codes включают `UNAUTHENTICATED`, `INVALID_CREDENTIALS`, `FORBIDDEN`, `RESOURCE_NOT_FOUND`, `COMPANY_NOT_FOUND`, `INVALID_STATUS_TRANSITION`, `SOURCE_DATA_INVALID`, `USE_ALTERNATIVE`, `OFFER_NOT_ELIGIBLE`, `SOURCE_UNAVAILABLE`, `INVALID_SOURCE`, `CALCULATION_INVALID`, `AUDIT_UNAVAILABLE`, `DATABASE_UNAVAILABLE`, `VALIDATION_ERROR`, `INTERNAL_ERROR`.

### 2.6. State machine

Канонические статусы:

```text
review
need_info
offer
sign
ready
disbursed
rejected
```

Разрешённые переходы определены централизованно:

| Из | В | Роль | Действие/API |
|---|---|---|---|
| `review` | `need_info` | `bank` | решение `need_info` |
| `review` | `offer` | `bank` | `approve` или `alternative` |
| `review` | `rejected` | `bank` | `reject` |
| `need_info` | `review` | `client` | `/additional-info` |
| `offer` | `sign` | `client` | `/accept` с `accepted=true` |
| `offer` | `rejected` | `client` | `/accept` с `accepted=false` |
| `offer` | `rejected` | `bank` | `reject`, отзыв оффера |
| `sign` | `ready` | `client` | `/sign` |
| `ready` | `disbursed` | `client` | `/disburse` |

Любая другая комбинация роли, действия и состояний возвращает `409 INVALID_STATUS_TRANSITION` без изменения заявки.

`additional-info` прикрепляет только существующие документы той же компании; неизвестный id возвращает `404`. Пустой `documentIds` допустим, комментарий обязателен. Endpoint не загружает файл, не меняет финансовый профиль и не выполняет новую оценку.

Клиентские transition endpoint’ы не являются идемпотентными: повтор после уже выполненного перехода обычно получает `409`.

### 2.7. Realtime

WebSocket аутентифицируется той же cookie или Bearer. При отсутствии валидной сессии backend закрывает соединение кодом `4401`. Текущий backend принимает входящие text frames только для поддержания соединения и не обрабатывает клиентские события; рабочий поток является server-push.

Envelope:

```json
{
  "id": "uuid-события",
  "sentAt": "UTC ISO 8601",
  "type": "application.updated",
  "payload": {
    "application": {}
  }
}
```

Фактически публикуются:

| Тип | Получатели | Payload |
|---|---|---|
| `application.updated` | все подключённые `bank`; `client` только той же компании | полный актуальный `application`; envelope также может содержать `applicationId` и `status` |
| `notification.created` | конкретный пользователь | полное уведомление |
| `notification.read` | конкретный пользователь | `notificationId` |

Routing metadata `companyId` и `userId` используется сервером, но удаляется из отправляемого envelope. `id` генерируется для публикации, `sentAt` ставится после commit.

`application.updated` публикуется после успешного commit для создания заявки, `additional-info`, accept/decline, sign, disburse и банковского решения. Первое прочтение уведомления публикует `notification.read`, а решение банка дополнительно публикует `notification.created`.

Frontend применяет полные payload локально, переподключается с exponential backoff 1, 2, 4… секунд до максимума 10 секунд, после повторного подключения перечитывает серверное состояние, опрашивает API раз в 15 секунд только для видимой вкладки и синхронизируется при `visibilitychange`. Код `4401` завершает reconnect и сбрасывает frontend-сессию. Polling остаётся страховкой от разрыва соединения или потерянного события, а не источником истины.

## 3. Grouped recommendations и audit semantics

### 3.1. Запрос

`POST /api/v1/recommendations` принимает строго типизированный объект:

```json
{
  "purpose": "goods",
  "amount": 800000,
  "termMonths": 24,
  "preference": "min_interest"
}
```

Поля:

- `companyId` — необязательная строка 1–128 символов; если передана, обязана совпасть с компанией текущего клиента;
- `purpose` — `goods | equipment | cash_gap`;
- `amount` — число или десятичная строка, `0 < amount <= 1e12`, максимум два десятичных знака; boolean, NaN и Infinity запрещены;
- `termMonths` — строгое целое 1–120; boolean запрещён;
- `preference` — `min_interest` по умолчанию или `min_payment`;
- дополнительные поля запрещены.

Frontend не передаёт финансы, score, каталог, версии или время. Любая попытка передать такие поля отклоняется как `422`. Backend загружает согласованный server-side snapshot авторизованной компании и всего каталога.

Чужая и отсутствующая компания неразличимы для клиента и возвращают одинаковый `404 COMPANY_NOT_FOUND`.

### 3.2. Ответ

Верхний уровень:

- `evaluationId` — новый UUID расчёта;
- `companyId`;
- `rankingVersion`;
- `preference`;
- `requestedAmount`;
- `requestedTermMonths`;
- `calculatedAt`;
- `groups`;
- `requestSummary` — точное совпадение, рассмотрение, изменённые альтернативы, недостаток сведений или отсутствие вариантов;
- `requestChecks` — проверка исходной суммы и срока по каждому продукту, даже при неподдерживаемом исходном сроке.

`evaluationId` идентифицирует расчёт, а не заявку и не бессрочное одобрение. Каждый повторный запрос создаёт новый id и отдельный audit record, даже при одинаковых входах.

Каждый `RankedOffer` содержит:

- `product` — публичный snapshot продукта;
- `evaluation` — полная оценка исходной запрошенной суммы на рассматриваемом сроке;
- `selectedEvaluation` — повторная оценка именно показанных условий;
- `stress` — чувствительность показанных условий;
- `highlights`, `comparisonAmount`, `comparisonCount` — сравнительные метки и область сравнения;
- `offer` — условия, которые нужно показывать пользователю;
- `termChanged`;
- `amountShortfall`;
- `group`;
- `rankInGroup`;
- `rankingReason`.

В `reduced_amount` `evaluation.eligible=false`, потому что исходная сумма не прошла, а `offer.eligible=true`, потому что уменьшенная сумма проверена отдельно. Уменьшенные суммы для score 50–69 остаются в requires_action с reviewRequired=true и eligible=false. Их прохождение строгой политики подтверждает selectedEvaluation.policyPasses. `evaluation.assessment` нельзя записывать в поле статуса заявки.

### 3.3. Группы и порядок

Потребитель обязан использовать следующий порядок явно, не полагаясь на порядок JSON-ключей:

1. `requested` — исходная сумма и желаемый срок проходят предварительные правила;
2. `other_terms` — исходная сумма проходит на другом поддерживаемом сроке;
3. `reduced_amount` — проходит меньшая сумма, возможно на другом сроке;
4. `requires_action` — `need_info`, `manual_review` или `blocked`;
5. `unavailable` — продукт/условия не подходят и проверенной альтернативы нет.

Для продукта с подходящей целью оцениваются все уникальные поддерживаемые сроки. Для продукта с неподходящей целью создаётся один объясняющий `unavailable`-вариант без размножения по срокам. Пустой каталог возвращает пять пустых групп, но не отключает валидацию запроса и компании.

Общего рейтинга между группами нет. Пустые группы можно скрывать. Только первые три группы содержат предварительно доступные варианты; ни одна группа не является банковским одобрением.

### 3.4. Сортировка

Для `requested` и `other_terms`:

- `min_interest`: сначала меньший `interestAmount`, затем меньший `monthlyPayment`;
- `min_payment`: сначала меньший `monthlyPayment`, затем меньший `interestAmount`.

Для `reduced_amount` первый критерий — большая доступная сумма; затем применяются выбранный и вторичный денежные критерии. Это предотвращает победу слишком маленького кредита только из-за меньшей абсолютной переплаты.

Оставшиеся tie-breakers для доступных групп:

1. меньшая абсолютная разница с желаемым сроком;
2. меньший срок;
3. id продукта по возрастанию.

`requires_action` и `unavailable` сначала отделяют selectedEvaluation.policyPasses=true, далее сортируют по большей сумме, выбранной денежной метрике, вторичной метрике, id продукта и сроку. Это не общий рейтинг доступности между группами. Перестановка каталога не должна менять ответ.

Score используется для допуска, но не для сортировки предложений одной компании. Покрытие отображается, но не максимизируется как самостоятельная цель.

### 3.5. Аудит рекомендаций

До успешного ответа backend обязан сохранить `RecommendationAudit`. Ошибка записи превращает запрос в `503 AUDIT_UNAVAILABLE`; успешный расчёт без аудита не возвращается.

Audit record версии `recommendation-audit-v1` содержит:

- `actorId`, `companyId`;
- версии `model`, `features`, `policy`, `ranking`;
- `profileVersion` и `catalogVersion` — SHA-256 канонического JSON соответствующих snapshot’ов;
- `inputSha256` — SHA-256 канонического JSON полного набора `company + products + request`;
- полный server-side входной snapshot и запрос;
- полный внешний результат.

`evaluation_id` является primary key. ORM запрещает update и delete audit-записей. Hash выявляет изменение входного JSON, но не является цифровой подписью и не заменяет контроль доступа.

Для воспроизведения нужны сохранённые входы, `calculatedAt` и соответствующая версия кода. Текущие строковые версии не связаны с Git SHA или build artifact — это production gap.

Ошибки рекомендаций:

| Код | HTTP | Значение |
|---|---:|---|
| `COMPANY_NOT_FOUND` | 404 | Компания отсутствует или недоступна actor. |
| `SOURCE_UNAVAILABLE` | 503 | Не удалось загрузить snapshot. |
| `INVALID_SOURCE` | 503 | Snapshot не имеет ожидаемой структуры/версий. |
| `SOURCE_DATA_INVALID` | 409 | Серверные профиль или каталог требуют исправления; это не кредитный отказ. |
| `CALCULATION_INVALID` | 503 | Расчёт не соответствует внешнему DTO. |
| `AUDIT_UNAVAILABLE` | 503 | Не удалось атомарно сохранить аудит. |

## 4. Decisioning: scoring, financing, ranking и stress

### 4.1. Общая валидация денег и времени

Расчётные денежные входы принимают `str | int | float | Decimal`, но не `bool`. Значение должно быть конечным, неотрицательным, не больше `1e12` рублей и иметь не более двух знаков после запятой. Пропуск, `null`, NaN, Infinity, отрицательное значение или неверный тип вызывают `InputError`; отсутствующее значение никогда не заменяется нулём.

Для principal дополнительно требуется `amount > 0`. Для ставки допустим диапазон 0–100 процентов годовых. Срок — строгое целое 1–120 месяцев.

`evaluated_at` — обязательный timezone-aware `datetime`, задаваемый backend; он нормализуется в UTC. Одинаковые входы и одинаковое время дают одинаковый финансовый результат, кроме внешних идентификаторов аудита.

### 4.2. Scoring компании

Версии:

- `modelVersion = rules-v1.0.0`;
- `featureVersion = company-v1`.

Обязательные входы:

| Поле | Контракт |
|---|---|
| `registrationDate` | Точная строка `YYYY-MM-DD`, не позже UTC-даты оценки. |
| `monthlyRevenue` | Месячная выручка, рубли. |
| `monthlyExpenses` | Операционные расходы того же периода без платежей по долгам. |
| `existingPayments` | Суммарные ежемесячные платежи по действующим долгам. |
| `hasOverdue` | Строгий boolean: есть текущая непогашенная просрочка на момент оценки. |

Legacy-поле `scoringScore`, ОКВЭД, продукт и условия кредита не являются входами score и игнорируются.

Обозначения:

```text
F = monthlyRevenue - monthlyExpenses
M = F / monthlyRevenue                         если monthlyRevenue > 0
C = F / existingPayments                       если existingPayments > 0
```

`M` не определена при нулевой выручке. `C` не определено при отсутствии существующих платежей. Бесконечность не возвращается.

Баллы:

| Фактор | Условие | Баллы |
|---|---|---:|
| Текущая просрочка | нет / есть | 30 / 0 |
| Операционная маржа | `M >= 20%` | 25 |
|  | `10% <= M < 20%` | 18 |
|  | `0 < M < 10%` | 10 |
|  | `M <= 0` или нулевая выручка | 0 |
| Покрытие существующих долгов при `F > 0` | `C >= 2` | 30 |
|  | `1.25 <= C < 2` | 22 |
|  | `1 <= C < 1.25` | 10 |
|  | `C < 1` | 0 |
| Нет существующих платежей | `F > 0` / `F <= 0` | 30 / 0 |
| Возраст бизнеса в полных календарных месяцах | `>= 36` | 15 |
|  | `12–35` | 10 |
|  | `6–11` | 5 |
|  | `0–5` | 0 |

Полные месяцы — разность календарных месяцев минус один, если день оценки меньше дня регистрации.

Итоговый score — сумма четырёх факторов, 0–100:

- `low`: score `>= 70`;
- `medium`: `50 <= score < 70`;
- `high`: score `< 50`.

Названия risk level исторически обратны величине риска: больше score лучше, а `low` означает низкий риск. Категория не является вероятностью и сама по себе не разрешает/запрещает выдачу.

Каждый factor содержит стабильные `code`, `label`, `value`, `points`, `maxPoints`, `positive`. `positive=true`, когда фактор набрал не менее половины доступных баллов; это не SHAP, причинный эффект или независимый статистический вклад. `eventProbability` для rule-based модели всегда `null`.

Контрольный пример: при регистрации `2020-01-01`, выручке 900 000, расходах 740 000, существующих платежах 120 000 и отсутствии просрочки сумма факторов `30 + 18 + 22 + 15 = 85`, risk level `low`.

### 4.3. Продукт и документы

Продукт для расчёта обязан содержать:

- непустые `id`, `name`;
- `0 < minAmount <= maxAmount`;
- непустой список сроков, каждый 1–120;
- ставку 0–100% с точностью до 0,01 процентного пункта;
- непустой список целей из `goods | equipment | cash_gap`.

Компания дополнительно содержит строгий boolean `active` и `documents`.

Обязательные виды документов:

```text
registry
statement
reporting
bki
```

Вид берётся из `kind`, а при его отсутствии — из `id`. Id и kind должны быть уникальными. Распознаются статусы `ready`, `verified`, `attention`; только `ready` и `verified` удовлетворяют обязательному комплекту, `attention` приводит к `need_info`. Отсутствующий или пустой список означает неполный комплект. Иные статусы и некорректная структура являются ошибкой исходных данных.

### 4.4. Аннуитет и стоимость

Версия политики: `financing-v1.3.0`.

Для суммы `A`, годовой ставки в процентах `rate` и срока `n`:

```text
r = rate / 1200
Praw = A / n                              при r = 0
Praw = A * r / (1 - (1 + r)^(-n))         при r > 0
P = ceil(Praw до копейки)
```

Регулярный платёж всегда округляется **вверх до копейки**, чтобы не занизить нагрузку.

График моделируется равными месячными периодами с `Decimal` precision 40:

```text
due = balance * (1 + r)
actualPayment = min(P, due), округление HALF_UP до копейки
newBalance = max(0, due - actualPayment)
```

Последний фактический платёж корректируется для погашения остатка. `totalRepayment` — сумма фактических платежей, `interestAmount = totalRepayment - A`.

Расчёт не является ПСК и не учитывает комиссии, страховки, дневной day-count, льготные периоды и досрочное погашение. Для крайне малых сумм округление может погасить долг раньше формального срока; в текущем каталоге такие суммы отсутствуют.

### 4.5. Покрытие нового кредита

```text
F = monthlyRevenue - monthlyExpenses
D = existingPayments + P
coverage = F / D
```

При положительной сумме кредита `D > 0`. Условие проверяется до округления отображаемого коэффициента:

```text
T = 1.50 для score 50–69, иначе 1.25
coverage passes ⇔ F >= T * D
```

Поэтому отображаемые `1.25×` после округления не гарантируют прохождение точной проверки. API возвращает coveragePasses, вычисленный через Decimal; UI использует этот флаг для интерпретации покрытия.

### 4.6. Предварительная оценка

`assessment` принимает:

```text
eligible
alternative
need_info
manual_review
blocked
unavailable
```

Стандартное прохождение требует score >= 70, покрытия >= 1.25 и соответствия каталогу. Для score 50–69 доступно рассмотрение: покрытие >= 1.50, сумма <= min(maxAmount, 50% месячной выручки), лимит округляется вниз до копеек. Все пороги — демонстрационные допущения проекта.

Приоритет: inactive/overdue/score<50 → blocked; неполные документы → need_info; несовместимая цель/срок или сумма ниже минимума → unavailable. После этого проверяются применимые лимиты и покрытие. Проходящий профиль 50–69 получает manual_review; стандартный — eligible. Если исходная сумма не проходит, ищется меньшая: для 50–69 результат остаётся manual_review с alternative; для стандартного пути — alternative. Если меньшая сумма не найдена — unavailable.

eligible=true означает только стандартное предварительное прохождение. reviewRequired обозначает диапазон 50–69. policyPasses=true подтверждает, что именно исходные условия проходят применимую политику; при наличии alternative это поле false. Выбранная альтернатива проверяется отдельно. Просрочка, неактивность, неполные документы и score<50 не исправляются уменьшением суммы.

reasons содержит все обнаруженные причины независимо от приоритетного исхода. Помимо code/message, возвращаются field, actual, minimum, maximum, allowedValues. AMOUNT_OUT_OF_RANGE явно сообщает минимум или максимум и запрошенную сумму; SCORE_TOO_LOW блокирует предложение, SCORE_REVIEW указывает на путь рассмотрения. REVIEW_AMOUNT_LIMIT и INSUFFICIENT_COVERAGE объясняют ограничения конкретных условий.

constraints содержит productMinAmount, productMaxAmount, allowedTerms, allowedPurposes, appliedAmountLimit, requiredCoverage, maxNewMonthlyPayment, monthlyCashFlow, totalMonthlyDebtPayment, requiredMonthlyRevenue и monthlyCoverageShortfall. Бюджет нового платежа округляется вниз до копейки, неотрицателен и сам по себе не гарантирует доступность кредита.

Структурированные actions содержат следующие действия: конкретные недостающие документы, проверку источника просрочки/реестра, повторный подбор или передачу на рассмотрение. Они не обещают повышения score. В карточке альтернативы причины и действия берутся из selectedEvaluation. Заявка сохраняет снимок действий при подаче; SUBMIT_APPLICATION после подачи не показывается, а после предложения банка исходные действия не выдаются за актуальные.

### 4.7. Альтернативная сумма

Бюджет нового платежа:

```text
B = F / T - existingPayments
```

Ищется максимальная сумма на сетке 10 000 рублей, которая:

- не превышает исходный запрос;
- не превышает применимый лимит суммы из раздела 4.6;
- не ниже `minAmount`;
- имеет округлённый вверх платёж `P <= B`.

Поиск выполняется двоично по монотонной функции платежа. Если сетка не дала сумму не ниже минимума, отдельно проверяется точный `minAmount`, поскольку минимум продукта может быть не кратен 10 000.

Кандидат должен быть строго меньше исходного запроса. После выбора заново рассчитываются платёж, стоимость и покрытие; нарушение порога считается внутренней арифметической ошибкой. Изменение срока и сравнение продуктов выполняет ranking, а не алгоритм суммы.

Контрольный пример для продукта 24% на 24 месяца и запроса 800 000 рублей:

- профиль с выручкой 900 000, расходами 740 000 и текущими платежами 120 000 получает альтернативу 150 000; 160 000 уже не проходит покрытие;
- профиль с выручкой 1 200 000, расходами 850 000 и текущими платежами 70 000 проходит исходный запрос;
- профиль с текущей просрочкой получает `blocked` без альтернативы.

### 4.8. Ranking

Версия: `ranking-v1.3.0`.

`recommend_financing` валидирует запрос и компанию даже при пустом каталоге, запрещает повторяющиеся product id, не мутирует входы и устраняет дубликаты сроков через `set`.

Группировка и сортировка соответствуют разделу 3. Важные инварианты:

- `requested` и `other_terms` всегда сохраняют полную запрошенную сумму;
- `reduced_amount` показывает отдельно проверенную альтернативу;
- `requires_action` не смешивается с доступными предложениями;
- score не участвует в сортировке;
- порядок каталога не влияет на результат;
- `rankInGroup` начинается с 1 отдельно в каждой группе.

### 4.9. Stress-сценарии

Версия: `stress-v1.2.0`.

`stress_financing` повторно оценивает **одну и ту же исходную сумму** при снижении выручки на 0%, 10%, 20%, 30%. Расходы, существующие платежи, ставка, срок, сумма и нефинансовые данные фиксированы. Новая выручка округляется `HALF_UP` до копейки.

Минимальная выручка для покрытия:

```text
Rrequired = monthlyExpenses + T * (existingPayments + P)
revenueHeadroom = monthlyRevenue - Rrequired
```

Если текущая выручка положительна и запас неотрицателен:

```text
maxRevenueDeclinePercent = 100 * revenueHeadroom / monthlyRevenue
```

Если исходное покрытие уже ниже порога или выручка равна нулю, `maxRevenueDeclinePercent = null`, а не вводящие в заблуждение 0%. На точной границе возвращается 0 и покрытие проходит.

Каждый scenario содержит `revenueDeclinePercent`, новую `monthlyRevenue`, `coveragePasses` и полную `evaluation`. Наличие положительного запаса не отменяет просрочку, документы, score или продуктовые ограничения. Вложенная уменьшенная `alternative` не меняет исследуемую исходную сумму.

Контрольный пример для выручки 1 200 000, расходов 850 000, существующих платежей 70 000 и кредита 800 000 под 24% на 24 месяца:

- платёж 42 296,88 рубля;
- `requiredMonthlyRevenue = 990 371,10`;
- запас снижения около 17,47%;
- сценарии 0% и 10% проходят покрытие, 20% и 30% — нет.

Это анализ чувствительности, а не прогноз бизнеса, банковский stress test или вероятность дефолта.

## 5. Проектные допущения

1. Rule-based baseline выбран сознательно: обучение на синтетических default labels создало бы ложную статистическую обоснованность.
2. Score измеряет проектную устойчивость, но не PD; `eventProbability=null` обязателен, пока нет валидной модели.
3. Веса факторов, score thresholds 50/70, coverage thresholds 1.25/1.50, лимит половины месячной выручки для 50–69, четыре обязательных документа, сетка альтернативы 10 000 рублей и порядок assessment выбраны командой как демонстрационная политика.
4. `monthlyRevenue`, `monthlyExpenses` и `existingPayments` относятся к одному месячному периоду. Расходы не включают debt service. Runtime пока не хранит `asOf`, source и freshness SLA этих признаков.
5. `hasOverdue` означает текущую непогашенную просрочку, а не любую историческую просрочку.
6. Статус компании и документы проверяются отдельно от score; ОКВЭД не влияет на score без утверждённой отраслевой политики.
7. Каталог содержит демонстрационные ставки; экономическое обоснование рыночных условий не выполнялось.
8. Аннуитет использует равные месячные периоды без комиссий, страховок и банковского day-count.
9. Ranking оптимизирует либо абсолютную процентную переплату, либо платёж; это не ПСК и не персонализированная ML-рекомендация.
10. В `reduced_amount` сохранение максимально возможной части потребности важнее минимизации абсолютной переплаты маленького кредита.
11. Stress предполагает неизменные расходы и существующий долг при снижении выручки; вероятности сценариев не назначаются.
12. Синтетические ФНС/БКИ/документы проверяют процесс, а не качество внешних источников.
13. Финансовые решения вычисляются через `Decimal`, но внешние DTO сериализуют деньги как JSON number для совместимости frontend.
14. Hash аудита обеспечивает воспроизводимость и обнаружение случайного изменения, но не криптографическое подтверждение происхождения.
15. Seed-заявки хранят score, рассчитанный действующими правилами на момент подачи; профиль пересчитывается по текущим данным, поэтому после изменения финансов или возраста бизнеса значения могут обоснованно отличаться.

## 6. Открытые решения и production gaps

### 6.1. Решения аналитика и продукта

Нужно явно утвердить либо изменить текущую реализацию:

1. финальный каталог, диапазоны сумм, сроки и ставки;
2. подтверждение проектных порогов score 50/70, coverage 1.25/1.50, лимита половины выручки, весов и сетки 10 000 рублей на реальных исходах;
3. владельца перехода `ready → disbursed`: сейчас его выполняет `client`;
4. состав сведений в `need_info`, возможность менять финансы и обязательность загрузки новых документов;
5. достаточность ограниченного пути manual_review 50–69 и полномочия сотрудника; произвольный обход блокирующих проверок не предусмотрен;
6. должно ли `alternative` быть только меньшей суммой/другим сроком и можно ли менять ставку; runtime сейчас принимает любое общее `eligible`-предложение;
7. срок действия рекомендации/оффера и связь `evaluationId` с заявкой;
8. допустимость создания заявки с `blocked`, `need_info`, `manual_review` или `unavailable` assessment;
9. обязательные machine-readable причины отказа, пользовательские warnings и тексты решений;
10. канонические подписи статусов и событий при сохранении текущих machine codes;
11. финальные seed-профили и контрольные расчётные примеры;
12. data dictionary: `asOf`, период, источник, owner и freshness SLA финансовых признаков;
13. приоритет и допустимый scope AI-помощника и stress UI относительно основного кредитного пути.

Для будущей ML-модели нужен отдельный target contract: определение события, prediction horizon, observation window, источник labels, правила censoring/leakage, train/evaluate split, calibration, fairness, monitoring и governance. Нельзя автоматически переносить текущие веса и пороги в обучаемую модель.

### 6.2. Безопасность

- Значение `AUTH_SECRET` по умолчанию известно и предназначено только для локальной разработки.
- `AUTH_COOKIE_SECURE` по умолчанию выключен; production требует HTTPS/WSS и Secure cookie.
- Logout удаляет cookie, но не отзывает Bearer и уже установленные WebSocket-сессии.
- `/demo/reset`, `/mocks/*`, `/assistant/chat`, каталог и logout не защищены ролью; destructive/demo endpoint’ы должны быть закрыты или удалены.
- WebSocket не проверяет `Origin`.
- CORS allowlist задан в коде, а не конфигурацией окружения.
- Auth читается вручную из `Request`, поэтому OpenAPI security scheme неполная.
- Нет refresh/revocation/session registry, rate limiting и зафиксированной политики brute-force protection.
- Для audit и финансовых snapshots не настроены retention policy, отдельные права чтения и шифрование на уровне приложения.

### 6.3. Данные и persistence

- По умолчанию используется SQLite; startup вызывает `Base.metadata.create_all` и автоматически seed’ит пустую БД.
- Миграций Alembic нет; PostgreSQL-схема и поведение блокировок не подтверждены.
- `ScoringRule` хранит `min_score` и `min_coverage`, но расчёт использует константы Python. Сейчас существуют две потенциальные точки истины policy.
- Версии правил не связаны с Git SHA, container digest или неизменяемым build artifact.
- Нет idempotency key для создания заявки и решений.
- Банковское решение использует `SELECT FOR UPDATE`, но нет optimistic version, системной защиты всех конкурентных переходов и подтверждённой семантики на production СУБД.
- Публичный application id вычисляется просмотром существующих id; конкурентное создание требует надёжной последовательности/уникального retry.

### 6.4. API и workflow

- Runtime OpenAPI и фактический error envelope рекомендаций расходятся; нужно оставить одну плоскую схему и добавить её ко всем responses.
- OpenAPI должен явно описывать cookie/Bearer security и фактическую защищённость каждого endpoint’а.
- Ограничения суммы различаются: recommendations допускает до `1e12`, создание заявки — только 50 000–5 000 000; бизнес-границы нужно унифицировать с каталогом.
- Создание заявки не запрещает недоступный assessment.
- `additional-info` не загружает новые файлы и не обновляет финансовые данные; оно только связывает существующие документы и комментарий.
- Статусы документов вне `ready | verified | attention` дают `SOURCE_DATA_INVALID`, а не процесс уточнения.
- Alternative decision не обязана быть меньше исходной суммы.
- Клиентские transition endpoint’ы не поддерживают идемпотентный повтор.
- Банковский list endpoint не поддерживает status/search/sort и не возвращает `limit/offset` в DTO.
- Frontend получает список, затем загружает детали пакетами по восемь, что остаётся N+1-паттерном; нужен rich/batch endpoint.

### 6.5. Realtime и эксплуатация

- Все workflow-мутации публикуют `application.updated`, но событие отправляется только после commit и без гарантии доставки или replay; polling ограничивает задержку рассинхронизации.
- Connection registry хранится в памяти одного процесса; несколько workers не обмениваются событиями.
- Нет broker/pub-sub и transactional outbox; событие после commit не имеет гарантированной доставки и replay.

- Нужны нагрузочные тесты HTTP/WebSocket, reconnect storm, slow consumers и отказ БД/broker.
- Требуются production secrets management, HTTPS/WSS, конфигурируемый CORS, health/readiness разделение, логирование request/correlation id и мониторинг.
- Полный чистый deployment должен проверять миграции, PostgreSQL, Nginx proxy для `/api/` и WebSocket Upgrade, а также end-to-end сценарии обеих ролей.

## 7. Уточнения DS и состояние интеграции на 25 октября 2026

### 7.1. Сводка запроса и сравнение

requestSummary возвращает статусы exact_available, exact_review, alternatives_available, information_required, unavailable и количества exactMatchCount, exactReviewCount, otherTermCount, reducedAmountCount. Другой срок не считается точным совпадением, рассмотрение не считается стандартным прохождением. requestChecks перечисляет исходные условия по каждому продукту. Frontend сохраняет полный grouped response, показывает сводку исходного запроса, проверки, отдельные секции групп, structured reasons/constraints и явные отличия альтернатив от запроса.

Метки сравниваются внутри группы на одинаковую сумму, только среди вариантов с selectedEvaluation.policyPasses=true. Требуются минимум два варианта и различия по показателю. Полностью одинаковые и одиночные варианты меток не получают; лучшие равные значения могут делить метку при наличии худшего конкурента. comparisonAmount и comparisonCount показывают область сравнения. Разные суммы не сравниваются по абсолютным процентам.

### 7.2. Stress в API и интерфейсе

Компактный stress_summary передаётся в рекомендациях для фактически показанных суммы и срока, сохраняется при подаче заявки и в аудите решения банка. Старые заявки без снимка не получают новый результат задним числом. В карточке заявки показан исходный запрос на момент подачи; предложение банка может отличаться.

Исходный порог T фиксируется для расчёта запаса и coveragePasses. В каждом сценарии заново проверяется вся политика: ухудшение score может изменить требования, поэтому прохождение исходного покрытия не означает policyPasses. Сценарии не меняют заявку или порядок ранжирования и не обязаны все проходить для положительного решения.

headroomStatus различает below_threshold, at_threshold, negligible и positive. Малый положительный запас <0.1% показывается как «менее 0,1%», а не 0.0%. Положительный процент от 0.1% в тексте округляется вниз до двух знаков. Точное maxRevenueDeclinePercent сохраняется.

Сценарии дополнены monthlyCashFlow, operatingDeficit=max(0,расходы−выручка), debtServiceShortfall=max(0,старые платежи+новый платёж−поток до долгов) и coverageExplanation. Отрицательное покрытие допустимо при операционном дефиците; выручка и платежи не становятся отрицательными. API также возвращает исходные выручку, расходы, платежи и coverageDefinition. Новые поля необязательны при чтении исторических снимков.

Контрольный пример «Города»: кредит 200 000, 24%, 36 месяцев; новый платёж 7 846.58, все платежи 127 846.58. Поток при 0/10/20/30% снижения — 160 000 / 70 000 / −20 000 / −110 000; покрытие около 1.2515 / 0.5475 / −0.1564 / −0.8604. Запас 0.0213083% практически отсутствует. Расходы и действующие платежи фиксированы.

### 7.3. Время, аудит и проверки

ApiSchema нормализует datetime в UTC. SQLite возвращает naive datetime из полей, которые сервис записывает в UTC: им восстанавливается UTC. Явные смещения переводятся в UTC с сохранением момента; даты регистрации без времени не меняются. Это устраняет потерю суффикса Z после повторного чтения заявки.

На 25 октября 2026 полный запуск `pytest` содержит 101 успешно пройденный тест. Проверены границы продукта в копейках, разные минимумы для одной суммы, исходный неподдерживаемый срок, отсутствие каталога/совпадений, 50–69, повторное решение после изменения профиля, неизменность исторического снимка, равные/одиночные предложения, перестановки каталога, независимый пересчёт стресс-примера, realtime после клиентских мутаций и сохранение комментариев истории после повторного чтения.

Frontend подключён к серверным профилям, каталогу, полному grouped recommendation contract, заявкам и действиям обеих ролей. Результаты подбора разделены по группам; показаны requestSummary, requestChecks, structured reasons/constraints, область сравнения, изменения суммы/срока, stress и точное время оценки. Комментарии видны в истории обеих ролей, загрузки используют общий skeleton, уведомления закрываются outside click и Escape. Полноценная загрузка новых файлов, PostgreSQL/миграции, идемпотентность, конкурентные операции и production hardening остаются отдельной работой.
