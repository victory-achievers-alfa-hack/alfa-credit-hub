# Контракт скоринга компании v1

Статус: реализован независимый Python-модуль, HTTP-интеграция ещё не выполнена. Версия правил `rules-v1.0.0`, версия признаков `company-v1`. Назначение — демонстрационная оценка устойчивости 0–100, больше значит лучше. Не PD, не банковский рейтинг и не самостоятельное решение о выдаче.

## Вызов

```python
from datetime import datetime, timezone
from backend.src.scoring import score_company

result = score_company({
    "registrationDate": "2020-01-01",
    "monthlyRevenue": 900000,
    "monthlyExpenses": 740000,
    "existingPayments": 120000,
    "hasOverdue": False,
}, evaluated_at=datetime(2026, 10, 23, tzinfo=timezone.utc))
# score = 85; factors[].points суммируются в score
```

Из корня alfa-credit-hub: `python -m unittest discover -s tests -v`.

## Входы

| Поле | Смысл и ограничения |
|---|---|
| registrationDate | Строка YYYY-MM-DD, дата регистрации не позже даты оценки в UTC |
| monthlyRevenue | Выручка за выбранный месячный период, рубли |
| monthlyExpenses | Операционные расходы за тот же период, без платежей по долгам |
| existingPayments | Суммарные ежемесячные платежи по действующим долгам, включая основной долг и проценты |
| hasOverdue | Обязательный boolean: есть действующая просроченная задолженность на момент оценки; погашенные старые просрочки сюда не входят |
| evaluated_at | Отдельный обязательный аргумент datetime с часовым поясом; задаётся сервером и нормализуется в UTC |

Деньги: конечное неотрицательное число или десятичная строка, не более двух знаков после запятой, максимум 1 трлн рублей для демонстрационного домена. Bool не считается числом. Пропуск, null, NaN, Infinity и неправильный тип — InputError с именем поля, а не автоматический ноль. Backend должен преобразовать ошибку в запрос корректных данных/валидационный ответ; текущий модуль не меняет статусы заявки.

Источник в демо — синтетический профиль компании. В интеграции backend обязан удостовериться, что финансовые поля относятся к одному периоду, имеют известный источник и актуальны; функция не может вывести это из трёх сумм. Время оценки необходимо сохранять для воспроизведения.

## Формулы и баллы

Операционный поток F = выручка − расходы. Маржа M = F / выручка. Покрытие существующих обязательств C = F / existingPayments. Новый кредит сюда не входит: его доступность проверяется отдельно.

| Фактор | Условия | Баллы |
|---|---|---|
| Текущая просрочка | Нет / есть | 30 / 0 |
| Маржа | M >= 20%; 10% <= M < 20%; 0 < M < 10%; M <= 0 или нулевая выручка | 25 / 18 / 10 / 0 |
| Покрытие существующих долгов | При F > 0: C >= 2; 1.25 <= C < 2; 1 <= C < 1.25; C < 1 | 30 / 22 / 10 / 0 |
| Нет существующих платежей | F > 0 / F <= 0 | 30 / 0 |
| Неположительный поток | Независимо от наличия долгов | 0 за покрытие |
| Возраст в полных календарных месяцах | >= 36; 12–35; 6–11; 0–5 | 15 / 10 / 5 / 0 |

Полные месяцы: разность календарных месяцев минус один, если день оценки меньше дня регистрации. Маржа при нулевой выручке не определена; покрытие при отсутствии платежей не определено. Не возвращаем бесконечность.

Итог = сумма четырёх вкладов. Категории по проектной шкале: low >= 70, medium 50–69, high < 50. Категория — описание балла, а не вероятность. Даже high не задаёт автоматически отказ, а low не отменяет блокирующие правила.

Веса выбраны как прозрачная первоначальная эвристика: история и текущая способность обслуживать долг имеют наибольший вес; маржа описывает запас доходности; возраст имеет меньший вес. Маржа и покрытие связаны общим денежным потоком, поэтому это не независимые свидетельства и не статистически оцененные коэффициенты. Значения не подгонялись под прежние 75/88/38 и требуют проверки продуктового поведения.

## Выход

Сохраняются совместимые поля `score`, `riskLevel`, `summary`, `factors[{label,value,positive}]`. Дополнительно возвращаются `modelVersion`, `featureVersion`, `calculatedAt`, `eventProbability: null`. Каждый фактор также содержит стабильный `code`, `points`, `maxPoints`.

`positive` означает получение не менее половины доступных баллов данного фактора; точное объяснение дают points/maxPoints. Это не SHAP и не причинный эффект. Изменение одного исходного поля может изменить несколько факторов.

## Границы ответственности

Модуль игнорирует legacy scoringScore. ОКВЭД сохраняется в профиле, но не влияет на балл без обоснованной отраслевой политики. Активность компании и документы — отдельные проверки. Сумма, срок, ставка, продукт, цель и покрытие нового кредита — входы следующего модуля оценки предложения. Таким образом, минимальный список из командного документа используется в системе целиком, но не помещается искусственно в один score.

Backend не должен использовать один score как условие одобрения: текущая просрочка может оставить числовой балл 70 и всё равно блокирует предварительное прохождение. Модуль предварительной оценки `assess_financing` уже реализован; его контракт описан в `financing_contract.md`. Интеграция с API и банковским процессом остаётся отдельным этапом.
