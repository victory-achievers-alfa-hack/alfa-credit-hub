# Расчёт и предварительная оценка финансирования v1

Реализован независимый модуль `backend/src/scoring/financing.py`. Он оценивает один продукт, сумму и срок. Не меняет статусы заявки, не выдаёт кредит и не записывает результат в БД. Версия политики `financing-v1.2.0`. Вызов не требует новых зависимостей или сети.

## Изменение политики 25 октября 2026

Стандартное прохождение: score >= 70 и покрытие >= 1.25. Для score 50–69 действует рассмотрение сотрудником: покрытие >= 1.50, сумма не больше 50% месячной выручки и максимума продукта. Лимит округляется вниз до копеек. Порог 50, покрытие 1.50 и доля 50% — допущения проекта; они не оценены на реальных дефолтах.

Для обоих путей обязательны действующая компания, отсутствие текущей просрочки, полный комплект документов и соответствие каталогу. Score < 50 блокирует предложение. Понижение суммы не снимает эти ограничения.

`eligible` означает только стандартное предварительное прохождение. `reviewRequired` обозначает диапазон 50–69. `policyPasses` говорит, что именно исходные условия проходят применимую политику; при наличии альтернативы это поле false. Альтернатива пересчитывается после выбора и остаётся требующей рассмотрения, если исходный профиль в диапазоне 50–69. `requiredCoverage` и `amountLimit` возвращают применимые ограничения.

Банк может одобрить проходящий вариант 50–69 с обоснованием не короче 20 символов после удаления пробелов по краям. Это проверка заполнения, а не автоматическая оценка качества обоснования. Сервер заново считает условия и сохраняет входы, результат, версию политики, автора и обоснование в `RecommendationAudit` в одной транзакции с решением. Исторический снимок заявки не перезаписывается.

Ниже сохранено описание базового алгоритма; правила диапазона 50–69 из этого раздела заменяют прежнее ограничение score >= 70 для любого положительного решения.

## Запуск и интерфейс

Из корня репозитория:

```bash
python -m examples.financing_demo
python -m unittest discover -s tests -v
```

```python
from backend.src.scoring import assess_financing, loan_quote

quote = loan_quote(800000, 24, 24)
result = assess_financing(
    company, product,
    purpose="goods", amount=800000, term_months=24,
    evaluated_at=evaluation_datetime,
)
```

`company`: входы скоринга из `ds_contract.md`, обязательный boolean `active` и список `documents[{id,status}]`. Отсутствующий/пустой список означает запрос документов, а не полный комплект. Обязательные id: registry, statement, reporting, bki. Все четыре должны иметь status=ready. Дубликаты, неизвестные статусы и некорректная структура — InputError. Поля времени/содержимого документов здесь не проверяются: это обязанность источника/мока проверки. Дополнительные документы не блокируют обязательный комплект.

`product`: id, name, minAmount, maxAmount, rate, terms, purposes. Суммы положительные, min <= max. Сроки — целые месяцы 1–120, годовая ставка 0–100 процентов с точностью до 0.01 процентного пункта. Цели: goods, equipment, cash_gap. Это ограничения входного домена прототипа, а не утверждение о допустимых банковских ставках.

`amount`: положительная сумма, до двух знаков после запятой. Остальные денежные границы и ошибки — как в контракте скоринга. `evaluated_at` фиксируется backend и сохраняется с входным снимком для повторения расчёта. Статусы проверки БКИ и hasOverdue приходят из одного актуального источника; модуль не разрешает противоречия между содержимым документов и данными профиля.

## Финансовая модель

Месячная ставка r = rate / 1200, число платежей n = term_months, сумма A.

- При r > 0: P = A * r / (1 - (1 + r)^(-n)).
- При r = 0: P = A / n.
- Регулярный платёж P округляется **вверх до копейки**, чтобы округление не занижало нагрузку.
- Проценты начисляются на остаток долга с точностью Decimal (40 знаков) за равные месячные периоды. Платежи ограничиваются остатком с начисленными процентами; последний платёж корректируется и округляется HALF_UP до копейки.
- totalRepayment — сумма фактических платежей по этой расчётной конвенции; interestAmount = totalRepayment - A. Это не ПСК. Комиссии, страховки, дневной day-count, льготные периоды и досрочное погашение в v1 не моделируются.
- Для крайне маленьких сумм округление может привести к погашению раньше n; последующие платежи нулевые. В текущем каталоге такие суммы отсутствуют.

Покрытие = (monthlyRevenue - monthlyExpenses) / (existingPayments + P). Новый кредит имеет положительный платёж, поэтому знаменатель здесь строго положительный. Нулевая/отрицательная выручка за вычетом расходов не заменяется благоприятным значением.

Проверка выполняется **до округления отношения**: поток >= 1.25 * (старые платежи + P). Отображаемые 1.25× после округления не гарантируют прохождение. Возвращаемые деньги сериализуются как JSON number в рублях, внутренние решения вычисляются через Decimal.

## Политика и порядок исходов

| assessment | Условие | Дальнейшее действие |
|---|---|---|
| blocked | Компания не действует или есть текущая просрочка | Банк рассматривает причину блокировки; уменьшение суммы не предлагается |
| need_info | Нет готового обязательного комплекта документов | Запросить сведения, затем пересчитать |
| unavailable | Цель/срок не подходят или сумма ниже минимума | Выбрать другой продукт/условия |
| manual_review | Балл < 70 при подходящей цели/сроке и минимуме | Передать профиль сотруднику; не обещать доступную альтернативу |
| eligible | Балл >= 70, сумма в диапазоне, покрытие >= 1.25, все проверки пройдены | Можно подавать/рассматривать заявку; это не окончательное одобрение |
| alternative | Исходная сумма не проходит, но меньшая проходит все проверки | Предложить её клиенту с объяснением и получить согласие |
| unavailable | Нет меньшей доступной суммы в диапазоне | Показать причины; предложить изменить другие условия |

Проверки идут сверху вниз. Все обнаруженные причины возвращаются независимо от приоритетного исхода. Ошибочные/отсутствующие обязательные финансовые данные вызывают InputError до решения, не получают фиктивный score или отказ. Backend преобразует их в валидационный ответ или процесс уточнения.

Оценка `assessment` **не является статусом заявки**. Её нельзя записывать вместо review/offer/need_info/... в state machine. `blocked` не выполняет автоматический переход в rejected.

## Альтернативная сумма

Бюджет нового платежа B = поток / 1.25 - существующие платежи. Ищем максимальную сумму на сетке 10 000 рублей, не превышающую запрос и максимум продукта, у которой округлённый платёж <= B. Используется двоичный поиск по монотонной функции платежа. Если сетка не даёт кандидата, отдельно проверяется minAmount (минимум продукта может не быть кратен 10 000).

После выбора заново рассчитываются платёж, стоимость и покрытие. Альтернатива должна быть строго меньше запроса и не ниже минимума продукта. При просрочке, неактивной компании, недостаточном score или документах она не возвращается. Изменение срока и сравнение других продуктов относятся к следующему модулю подбора.

## Выход

- productId, purpose, amount, rate, termMonths.
- monthlyPayment, lastPayment, totalRepayment, interestAmount, coverage.
- eligible: прохождение **исходного** запроса.
- assessment и reasons[{code,message}]: стабильные машинные коды и объяснения.
- alternative: null либо рассчитанные параметры меньшей суммы с coverage и eligible=true.
- recommendedAmount: сумма alternative либо null; само по себе поле не заменяет исход eligible.
- scoring: полный результат версии правил компании.
- policyVersion, calculatedAt: аудит решения.

DTO пока внутренний; он не является drop-in заменой frontend Recommendation (там также нужен product, reason и warning). При интеграции backend должен собрать внешний ответ, описать его в OpenAPI и сохранить снимок входов. Фиксированный scoringScore frontend использовать нельзя.

## Приёмочные сценарии

Для оборотного кредита 800 000 рублей, 24% годовых, 24 месяца, дата оценки 23.10.2026:

- «Город»: балл 85, недостаточное покрытие исходного запроса, альтернатива 150 000 рублей проходит; 160 000 уже не проходит.
- «Зёрна»: балл 100, исходный запрос проходит предварительные правила.
- «Вектор»: балл 20, текущая просрочка блокирует прохождение, альтернативы нет.
- Новый профиль с финансовыми данными «Зёрна» и пустым списком документов: need_info.

Сценарии воспроизводятся командой выше. Тесты дополнительно проверяют нулевую ставку, контрольные платежи независимой формулой, пороги, округление, высокий score при блокировке, неполные документы, ограничения каталога и максимальность альтернативы перебором допустимой сетки.
