# Подбор и ранжирование v1

Функция `backend.src.scoring.recommend_financing(company, products, *, purpose, amount, term_months, evaluated_at, preference="min_interest")`. Входы компании и продуктов соответствуют financing_contract.md. Это независимый внутренний модуль: HTTP и интерфейс ещё не подключены.

Для подходящей цели проверяются все уникальные сроки продукта. Каждый вариант проходит assess_financing; при необходимости берётся уже проверенная уменьшенная сумма. Не подходящий по цели продукт сохраняется один раз в unavailable с причиной. Дубликаты id продуктов и некорректные поля вызывают InputError. Пустой каталог допустим, но не отключает валидацию запроса и компании.

## Группы в порядке отображения

1. requested: полная сумма и желаемый срок, предварительные правила пройдены.
2. other_terms: полная сумма, другой срок; изменение явно обозначено termChanged.
3. reduced_amount: меньшая сумма; показываются amountShortfall и возможное изменение срока.
4. requires_action: нужны документы, ручное рассмотрение или устранение блокировки.
5. unavailable: продукт/условия не подходят, доступной альтернативы нет.

Возвращается groups с пятью именованными массивами. Потребитель должен соблюдать этот порядок явно, а не полагаться на порядок ключей JSON. Пустые группы можно скрывать. Общего рейтинга между группами нет.

## Сортировка

В requested и other_terms preference=min_interest означает сначала меньшую interestAmount, затем monthlyPayment. preference=min_payment меняет их местами. Это переплата только по процентам в текущей модели без комиссий и страхования, не ПСК.

В reduced_amount сначала большая доступная сумма, затем выбранные денежные критерии. Иначе маленький кредит победил бы только из-за меньшей абсолютной переплаты. Это явное проектное решение: сохранить максимум потребности важнее цены меньшей суммы.

При равенстве критериев: меньшая разница с желаемым сроком, меньший срок, id продукта по возрастанию. Поэтому перестановка каталога не меняет ответ. requires_action и unavailable сортируются по id продукта и сроку: этот порядок не является финансовой рекомендацией.

## Результат

rankingVersion=ranking-v1.0.0, preference, requestedAmount, requestedTermMonths, calculatedAt, groups.

Каждый элемент содержит product (независимая копия), evaluation (полная оценка первоначальной суммы на рассматриваемом сроке), offer (показываемые условия), termChanged, amountShortfall, group, rankInGroup, rankingReason.

У уменьшенной альтернативы offer.eligible=true, а evaluation.eligible=false: первоначальная сумма не прошла. У предложения без уменьшения offer отражает исходную оценку. Только первые три группы содержат предварительно доступные предложения. Никакая группа не означает окончательного одобрения банка и не меняет статус заявки.

Score компании используется для допуска, но не для сортировки её предложений. Покрытие показывается в offer, а не максимизируется как самостоятельная цель. Недостающая сумма, платёж, срок и переплата дают клиенту явные компромиссы.

## Проверка

`python -m unittest discover -s tests -v`

tests/test_ranking.py проверяет переключение предпочтения, сохранение желаемого срока отдельной группой, уменьшенные суммы, блокировки и документы, стабильные ничьи, перестановку каталога, отсутствие мутаций и дубликатов сроков, пустой каталог и ошибочные запросы.

Основание: PDF задания, стр. 14–15 (продукт и условия влияют на решение, допустимы иные сумма/срок), Идеи.txt и принятый план DS. Порядок групп и критерии — наша демонстрационная политика, не банковский стандарт. Backend должен описать внешний DTO в OpenAPI перед интеграцией; текущий frontend Recommendation не подменяется этим ответом напрямую.

## Диапазон 50–69, ranking-v1.1.0

Условия для рассмотрения остаются в requires_action, даже если вычислена меньшая сумма. Поле offer содержит рассчитанную альтернативу, reviewRequired=true, eligible=false. Такие условия нельзя отображать как стандартное прохождение. Проверяются отдельные ограничения financing-v1.1.0.
